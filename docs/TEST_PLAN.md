Every feature in Aeolus lands with at least one
integration test and, where it drives the UI, an E2E test. This
table is the canonical feature-to-test mapping. Update it in the

## Tiers

1. **Unit (Vitest)** — pure functions, no IO. `packages/*/src/**/*.test.ts`.
2. **Integration (Vitest + Testcontainers)** — a real Postgres 16 per
   suite; `MemoryBlobStore` stands in for S3 in most suites, MinIO
   where object semantics matter (`quay.io/minio/minio`, pinned to a
   dated `RELEASE.*` tag in `helpers/compile-fixtures.ts` — Docker
   Hub's `minio/minio` repository vanished 2026-09 and took the six
   compile suites down). `tests/integration/*.test.ts`.
   (Redis was removed when the session store moved to Postgres.)
3. **End-to-end (Playwright)** — real Chromium against the full stack.
   `tests/e2e/global-setup.ts` boots a Postgres testcontainer, runs
   migrations, starts api + ws + the compile worker in-process, then
   spawns Vite. `tests/e2e/*.spec.ts`. Most specs seed a session through
   the dev route so they can be about the feature under test;
   `first-run.spec.ts` is the one that types a real email and passphrase
   into the shipped screens.
4. **The shipped install (Playwright, against `docker compose`)** —
   `scripts/compose-smoke.mjs`, driven by `.github/workflows/docker.yml`.
   Not the in-process stack: the three real images, on the real
   `docker-compose.yml`, reached through Caddy on one port. It is the only
   tier that can catch a broken Dockerfile, a missing compose environment
   variable, or install instructions that no longer work.
5. **Visual regression** — *not implemented.* No `tests/e2e/visual/`
   directory exists; screenshot diffing was planned and never built.
   Listed here so the gap is explicit rather than implied by silence.

## Rules

- A feature is not "done" until its test is green in CI.
- Tests must not be skipped or `.only`'d on `main`.
- No mocking of the database in integration tests — use a real
  Postgres via Testcontainers.
- Suites that are *about something else* seed a session directly
  (`POST /api/dev/sessions`, behind `AEOLUS_ENABLE_DEV_ROUTES=1` and
  automatic under `NODE_ENV=test`), so a document or compile test stays
  about documents and compiles.
- The sign-in path itself is never stubbed. Aeolus checks the credential
  itself, so there is nothing unreachable to stand in for:
  `tests/integration/auth.passphrase.test.ts` drives `POST /api/auth/login`
  against a real server and a real Postgres,
  `tests/e2e/first-run.spec.ts` drives it through the shipped screens, and
  `scripts/compose-smoke.mjs` drives it against the compose stack with the
  credential read out of the api's log.
- Compile tests assert the produced PDF starts with `%PDF-` and is
  at least 1KB.

## Deployment verification

The shipped deployment is the `docker compose` stack at the repository
root. Verifying it is not a manual checklist:
`.github/workflows/docker.yml` runs the whole thing on every push to
`main` and every pull request against it, from a clean checkout with
nothing but Docker.

| Check | How verified |
| --- | --- |
| A stock `.env` is enough. | The job copies `.env.example` to `.env` and appends one generated `AEOLUS_COOKIE_SECRET` — the single value with no default — with the same `openssl rand -base64 48` the file tells a person to run. |
| All three images build. | `docker compose build --progress plain`. A cold worker build is ~10 minutes: it compiles the Landlock helper and pulls Tectonic and Typst, so the job carries a buildx layer cache. |
| The stack answers on one port. | `curl -fsS http://localhost:8080/healthz` inside a 90-second poll. On failure the job prints `docker compose ps` and the last 200 log lines rather than just the exit code. |
| **Every** process is running, not only the one behind the port. | `docker compose ps` must report `running` for `caddy`, `api`, `ws`, `worker`, `postgres` and `minio`. A worker that exited leaves compiles queued forever and the app looks fine until someone presses compile. |
| The worker said what its sandbox is doing. | `docker compose logs worker` must match `sandbox mode=(audit\|enforce)`. That line is what tells an operator whether they can turn enforce on; if it is missing, the worker is confining nothing and not saying so. |
| The install instructions still work. | `node scripts/compose-smoke.mjs` — the compose-smoke row in the table above. Screenshots of every stage upload as an artifact, so a CI failure can be looked at rather than guessed at. |
| The stack comes down cleanly. | `docker compose down -v`, always, so a failed run does not poison the next one. |
