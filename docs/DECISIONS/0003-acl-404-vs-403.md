# 0003 — Return 404 (not 403) for unauthorized document reads

- **Date**: 2026-04-14
- **Status**: Accepted
- **Phase**: 05 (document model + ACL enforcement)

> Originally specified in the phase-05 prompt as
> `0002-acl-404-vs-403.md`; renumbered to 0003 because 0002 is
> already taken by `0002-drizzle-orm.md`.

## Context

Aeolus's document model has five roles to enforce on
every route:

- admin (always `owner` regardless of the row)
- doc owner (`docs.owner_id`)
- editor collaborator (`doc_collaborators.role = 'editor'`)
- viewer collaborator (`doc_collaborators.role = 'viewer'`)
- non-member

The question for phase 05 was: when a non-member calls `GET /docs/:id`
or `PATCH /docs/:id` on a document they have no business knowing about,
what status code do we return?

The two credible options:

1. **`403 Forbidden`** — semantically "the server understands the
   request but refuses to authorize it". This is the textbook answer
   when the resource exists but the caller lacks access.
2. **`404 Not Found`** — indistinguishable from a truly missing
   document. Hides the existence of the row from callers that should
   not even know it is there.

## Decision

**Return 404 for all reads a caller is not authorized to perform.**
This applies uniformly to:

- `GET /docs/:id`
- `PATCH /docs/:id` when the caller has no read access
- `DELETE /docs/:id` when the caller has no read access
- `POST /docs/:id/collaborators` when the caller has no read access
- `DELETE /docs/:id/collaborators/:userId` when the caller has no
  read access

For callers that *do* have read access but lack write access (i.e. a
viewer trying to PATCH, or an editor trying to DELETE), we return
`403 Forbidden`. The viewer already knows the doc exists — there is
nothing left to leak — and a concrete 403 is a better UX than a
confusing 404.

The same rule applies to soft-deleted documents: for non-admins, a
soft-deleted row is `none` as far as the ACL helper is concerned, so
every route returns 404. Admins bypass the soft-delete filter via
`resolveRole` returning `owner` regardless of `deleted_at`.

Malformed doc ids (not parseable as a UUID) also short-circuit to
`none` in `resolveRole` before hitting the database, so the API
returns 404 without leaking any distinction between "invalid id" and
"id that does not exist".

## Consequences

- **Pro**: a hostile or curious user cannot enumerate document ids
  by watching for 403 vs 404. Every unauthorized read looks
  identical to a miss. This is consistent with the threat model in
  `docs/SECURITY.md`: the network an instance sits on is not a control
  Aeolus can rely on, so the ACL assumes an authenticated account is
  probing the API.
- **Pro**: routes handlers stay simple — they call a single helper
  (`assertCanRead` or `assertCanWrite`) and translate the thrown
  error into the response. No inline branching on role.
- **Pro**: easy to test exhaustively: the matrix in
  `tests/integration/docs.acl.test.ts` has a single non-member persona
  that receives 404 on every endpoint, which would have been split
  403/404 under the textbook answer. `tests/integration/route-acl.test.ts`
  asserts the browser plane and `/api/v1` answer that matrix identically.
- **Con**: technically violates the HTTP spec's intent that 404
  means "does not exist". We accept this because "does not exist
  *for you*" is a reasonable reading and the existence-leak risk
  outweighs strict compliance.
- **Con**: client code cannot distinguish "document was deleted" from
  "you were removed from the ACL" — both surface as 404. We accept
  this; neither case is actionable in the editor UI.

## Alternatives considered

- **Always 403** — rejected. Leaks existence of every document an
  admin has ever created. In a system where doc ids are UUIDs this
  is mild but non-zero risk, and cheap to eliminate.
- **Mixed** (404 for GET, 403 for mutation) — rejected. Mutation
  endpoints are exactly the ones where an attacker probing ids
  benefits most from a 403/404 side channel.
- **404 for non-members, 403 for viewers on writes** — accepted.
  Viewers already know the doc exists, so the existence-leak
  argument does not apply. This keeps the error message honest for
  the common case of "you have read access but can't edit this".

## Follow-ups

- Phase 06 (`apps/ws/...`) reuses `resolveRole` when authorizing
  WebSocket upgrades for Yjs. The same 404-vs-403 rule applies: an
  upgrade for a doc the caller cannot read is refused with a
  generic `404 Not Found` response on the HTTP upgrade, not a 403.
- Phase 08 (templates / forking) creates a fresh doc owned by the
  caller — no new ACL surface, but the fork endpoint must run
  `assertCanRead` on the source template first.
